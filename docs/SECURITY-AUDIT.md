# Engineering audit — 2026-10-20

Baseline: 1.1.1; candidate: 1.2.0-rc.1. Review was local engineering validation, not an independent penetration test or exhaustive OWASP certification.

Before source changes, the complete plugin directory (including its Git metadata) and the entire local WordPress database were backed up privately outside the webroot. The SQL dump contains original schema and data, including options, authentication metadata, activity, findings and security state. Ten relevant table definitions were extracted and a SHA-256 manifest recorded. Actual tables are wp_gwqsh_*; the requested wp_gracewell_* names do not exist here. No replacement tables, migration or schema-version bump was introduced.

All 83 baseline PHP files passed php -l. Targeted code review covered centralized AJAX capability/nonce dispatch, trusted path and quarantine primitives, early Guardian mutation, data-only signed feed schemas, feed replay/rollback and report output. No publisher private keys/API credentials were added. This is not proof that every code path is free of vulnerabilities. See SECURITY-GAPS.md for fixed issues and open work.

Fresh WordPress 6.8.3 was downloaded with WP-CLI (archive MD5 verified by WP-CLI), installed into /private/tmp/gracewell-upgrade-wordpress with a separate gracewell_upgrade_20261020 database and gwtest_ prefix. Only Gracewell was activated. XAMPP PHP 8.2.4/MySQL ran the functional tests. Plugin Check was installed as a development inspection tool. The original live database was not used for tests.

Plugin Check 2.1.0 runtime scan: five errors, 57 warnings. The baseline scan also had five errors (43 warnings). The errors are the existing Update URI header, which is disallowed for WordPress.org-hosted plugins, and four native PHP 8 string helper calls flagged against the WordPress 5.3 minimum. PHP >=8 is already required, so those helper findings require compatibility-tool disposition, not a claim of exploitability. The Update URI is intentionally retained for external distribution. New warnings predominantly concern direct reporting queries and raw controller inputs validated by existing filters. Fixed category SQL and prepared predicates have narrow, explained annotations; remaining findings stay visible. Development tests/tools are excluded from the runtime scan and ZIP.

The root contains no Composer manifest/lock, so root composer audit cannot run. A separate audit manifest/lock in tools/dependency-audit for the declared bundled lbuchs/webauthn 2.2.0 returned no published advisories or abandonment. This is metadata advisory screening, not an audit of namespace-scoped vendored code. Packagist source: https://packagist.org/packages/lbuchs/WebAuthn . No dependency implementation was silently replaced.

All 87 final PHP files pass lint; 28 protected UI source/assets match the backup byte-for-byte. The existing owned MU Guardian was separately backed up and regenerated from candidate sources with its original private-state declaration preserved, without loading the live WordPress database. Evidence JSON is in docs/evidence. SECURITY.md and the validation documents distinguish existing capability, changed behavior and untested requirements.
